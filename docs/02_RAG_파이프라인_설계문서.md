# RAG 파이프라인 설계문서 — FinRAG

## 1. 전체 흐름

```
[오프라인 · 1회]
KRX 시세(순위) ─▶ DART 기업개황 ─▶ 위키 문서 매핑 ─▶ data/items.json ─▶ company_meta (기업 1 = 청크 1)
한국은행 800선 PDF ─▶ 목차 순서 파싱 ─▶ glossary (용어 1 = 청크 1)

[질문할 때마다]
기업 선택 + 질문
 ├─ P1 검색어 추출 ─▶ 기업 자신의 이름 제외 ─▶ 수집 캐시에 없는 검색어만
 ├─ 기업 본문서(위키) — 처음 한 번, 선별과 상관없이 항상 수집
 ├─ 위키 검색 후보(제목·요약) ─▶ P2 선별 (+ 제목이 검색어와 같으면 규칙으로 포함) ─▶ 본문 수집
 ├─ DART 최근 정기보고서 — 기업별 처음 한 번, 'I. 회사의 개요'·'II. 사업의 내용'만
 ├─ 청킹 ─▶ company_docs 색인
 └─ LangGraph
      retrieve : 메타 1청크(검색 없이) + 기업 본문서 2청크 + 그 기업 범위 Top-k(유사도/MMR) + 용어집 ─▶ 중복 제거 ─▶ [근거 1..N]
      generate : P3 ─▶ 답변 ─▶ [근거 N] 파싱 ─▶ 인용된 근거만 화면에
```

LangGraph는 명세대로 `retrieve → generate` 두 노드다(`python scripts/show_graph.py`). 수집은 화면에 단계별 진행 상태를 보여 주기 위해 그래프 앞단의 함수로 두었다.

## 2. Vector DB 컬렉션 구조

명세의 두 컬렉션(항목 메타데이터 / 외부 문서)에 더해, 기업과 무관한 공용 근거인 용어집을 세 번째 컬렉션으로 분리했다.

| 컬렉션 | 단위 | 청크 ID | 메타데이터 | 비고 |
| --- | --- | --- | --- | --- |
| `company_meta` | 기업 1 = 청크 1 | `{종목코드}` | stock_code, corp_code, name, aliases, est_year(int), acc_month(int), rank, wiki_title, source_type=meta, title, source_url(DART) | ID 고정 → 재색인해도 덮어쓰기만 |
| `company_docs` | 문서 청크 | `{종목코드}:{wiki/dart}:{문서ID}:{순번}` | stock_code, company_name, source_type, title, source_url, doc_id(위키 pageid / DART 접수번호), section(공시), query, collected_at, doc_date, seq | 여러 기업이 같은 위키 문서를 모아도 종목코드가 달라 서로 덮어쓰지 않음 |
| `glossary` | 용어 1 = 청크 1 | `term:{번호}:{순번}` | term, page, related, source_type=glossary, title(용어 + 쪽), source_url, doc_date | 기업 필터 없이 검색 |

- **종목코드는 문자열**로 저장한다. `005930`을 숫자로 바꾸면 `5930`이 되어 ID·필터·DART 매핑이 전부 어긋난다.
- **`stock_code` 필터가 핵심**이다. 빠지면 다른 기업의 문서가 근거에 섞인다.
- `doc_date`를 둔 이유: 위키(수집 시점 스냅샷)와 공시(접수일이 분명)가 다른 말을 할 때 기준일을 함께 보여 주기 위해서다.
- Chroma 메타데이터는 스칼라만 허용 → 별칭·연관어는 문자열로, 연도·월은 숫자로 저장(고도화에서 `where` 필터로 활용 가능).

## 3. 문서 수집 · 청킹 · 색인 흐름

### 3.1 위키백과 (질문마다)
1. P1이 위키 문서 제목이 될 1~3단어 명사를 최대 4개 뽑는다. 기업 자신의 이름은 뺀다(본문서로 따로 넣고, 이름 검색은 동음이의어·그룹 문서를 끌어오기 때문).
2. 수집 캐시에 없는 검색어만 위키 검색(검색어당 후보 5개).
3. P2가 후보의 **제목과 요약만** 보고 고른다 — 본문을 받기 전에 버릴 문서를 정해 외부 호출과 임베딩 비용을 줄인다.
4. 제목이 검색어와 정확히 같은 후보는 규칙으로 살린다(P2가 지나치게 보수적일 때 대비).
5. 동음이의어 문서는 본문 수집 단계에서 제외한다.
6. 1,000자 / 200자 중복으로 청킹, 문서당 최대 30청크.

### 3.2 DART 정기보고서 (기업별 처음 한 번)
1. 공시검색으로 가장 최근 정기보고서(사업·반기·분기)를 찾는다 — 사업보고서보다 최신 수치를 쓸 수 있다.
2. 원문 zip을 받아 'I. 회사의 개요'와 'II. 사업의 내용' 하위 목차만 남긴다(자본금 변동·주식 총수·정관은 제외). 보고서 대부분은 재무제표 주석이라 다 넣으면 비용과 검색 노이즈만 커진다.
3. 표는 `<TR>` 단위로 `칸 | 칸 | 칸` 한 줄로 바꾼다(DART는 칸 태그로 TD·TH 외에 TE·TU를 씀).
   (고도화) 합친 칸(ROWSPAN·COLSPAN)을 펼쳐 모든 행의 칸 수를 머리글과 맞추고, 머리글 행은 `[표 머리글]`로 표시해 표 중간에서 시작하는 청크마다 다시 붙인다(`split_dart`).
4. 1,500자 / 200자 중복, 청크 앞에 `[II. 사업의 내용 > 4. 매출 및 수주상황]`처럼 목차를 붙인다. 보고서당 최대 60청크.

### 3.3 한국은행 용어집 (오프라인 1회)
1. 목차(789개)를 먼저 읽고, 본문은 **목차 순서상 다음에 나올 용어**만 기다리며 경계를 찾는다(해설 속 짧은 줄을 용어로 오인하지 않도록).
2. 홀수·짝수 쪽의 머리글·꼬리말 형식이 달라 둘 다 제거하고, 두 줄로 나뉜 목차 항목은 이어 붙인다 → 779/789개(98.7%) 파싱.
3. 용어 1개 = 청크 1개(가장 긴 해설 약 2,000자). 자르면 정의가 끊긴다.

### 3.4 출처별 방식을 다르게 한 이유 (F2016)

| 출처 | 문서 성격 | 수집 | 청킹 |
| --- | --- | --- | --- |
| 위키백과 | 짧고 문단이 의미 단위, 최신성 불명 | 질문마다 필요한 것만 | 1,000 / 200 |
| DART 정기보고서 | 수백 쪽, 표 위주, 기준일 명확 | 기업별 1회, 두 장만 | 1,500 / 200, 표 행 문장화 |
| 한국은행 용어집 | 용어별 정의가 완결된 단위 | 오프라인 1회 | 용어 1개 = 1청크 |

## 4. 검색 결과 병합과 중복 제거 (F2006)

retrieve 노드는 아래 순서로 근거를 모으고 **청크 ID 기준으로 중복을 제거**한 뒤 번호를 고정한다.

1. **선택 기업의 메타 청크** — 검색 없이 ID로 가져와 항상 [근거 1]
2. **기업 본문서 청크 2개** (`own_doc_k`) — '반도체'(204청크) 같은 긴 일반 문서가 Top-k를 독차지하는 것을 막는다
3. **그 기업 범위의 외부 문서 Top-k** (`top_k: 6`) — 검색 질의 앞에 기업명을 붙여 "이 회사" 같은 질문도 맞게 검색
4. **용어집** — 질문에 용어가 그대로 나오면 우선 포함(괄호 속 약어·슬래시로 나뉜 이름 포함), 임베딩 결과는 관련도 0.45 이상일 때만 최대 2개

번호는 retrieve에서 한 번만 매기고 state에 저장한다. generate와 화면은 이 번호로만 근거를 찾으므로 본문 번호와 화면 목록이 어긋나지 않는다.

## 5. 프롬프트 설계

| 프롬프트 | 역할 | 입력 | 출력 형식 | 핵심 규칙 |
| --- | --- | --- | --- | --- |
| P1 검색어 추출 | 증권사 기업분석 리서치 애널리스트 | 기업 색인 텍스트 + 질문 | `QueryPlan {queries: [str]}` (구조화 출력) | 1~3단어 명사, 문장형 금지, 기업 자신의 이름 제외, 최대 4개 |
| P2 후보 선별 | 기업 리서치 자료 큐레이터 | 질문 + 후보 번호·제목·요약 | `Selection {selected: [int], reason}` | 질문에 나온 회사·핵심 개념 문서는 고름, 이름만 같은 회사·인물·동음이의어 제외 |
| P3 답변 생성 | 근거 기반 기업 정보 안내원 | `[근거 N] (출처 유형) 제목 · 기준일` + 본문 목록, 기업, 질문 | 자연어 + `[근거 N]` | 근거 밖 내용 금지 · **여러 근거를 엮어 새 결론 금지** · 숫자·날짜엔 근거 번호 · 출처가 다르면 둘 다 제시 · 투자 판단 거절 · 근거 없으면 "제공된 문서에서 확인되지 않습니다" |

- P1·P2를 구조화 출력(Pydantic)으로 받는 이유: 자유 텍스트를 문자열로 파싱하면 형식이 조금만 달라져도 깨진다. 실패하면 서비스는 멈추지 않고 기업 본문서만으로 계속한다.
- 특화 기능(브리핑·팩트체크·용어 풀이)은 그래프를 따로 만들지 않고 P3에 작업 규칙(`TASK_RULES`)만 바꿔 넣는다 → 모든 기능이 같은 근거 검색·인용 검증을 거친다.

## 6. 청크 크기 · 중복 길이 · Top-k

| 설정 | 값 | 이유 |
| --- | --- | --- |
| 위키 청크 | 1,000자 / 200자 | 위키 문단 2~3개 분량. 중복 200자로 경계에서 끊긴 문장을 앞뒤 청크가 공유 |
| 공시 청크 | 1,500자 / 200자 | 표 행이 길고, 문맥 단위(목차 하나)가 커서 위키보다 크게 |
| 용어집 | 2,000자 / 0 | 용어 하나를 자르지 않기 위해 가장 긴 해설에 맞춤 |
| Top-k | 6 (+ 메타 1 + 본문서 2 + 용어집 최대 2) | 근거가 너무 적으면 다른 출처를 못 보고, 너무 많으면 작은 모델이 핵심을 놓침 |

**값을 바꿨을 때의 차이** (실측, `docs/eval/verification_log.md`)

- 청크 크기: '카카오 (기업)' 문서 4,380자 → 500/100: **14청크** · 1,000/200: **7청크** · 1,500/200: **5청크**
- Top-k (SK하이닉스 HBM 질문): k=3 → 근거 4개(기업정보·본문서·고대역 메모리), k=6 → 7개, k=10 → 11개(DART 반기보고서 '회사의 개요'·'연혁'이 추가로 들어옴). k가 커질수록 출처 종류는 늘지만 같은 문서 청크가 반복된다.
- MMR (F2014, `docs/eval/mmr_comparison.md`): 4개 질문 모두 근거 청크 간 평균 유사도가 낮아짐 (삼성전자 0.649 → 0.450, SK하이닉스 0.548 → 0.387). 같은 문서 청크가 몰리는 현상을 줄인다.

## 7. 근거 표시 방식 (F2008)

1. P3가 문서에서 온 주장마다 `[근거 N]`, 여러 개면 `[근거 1, 3]`을 붙인다.
2. 정규식 `\[근거\s*([\d,\s]+)\]`로 번호를 뽑아, retrieve가 고정한 번호와 일치하는 근거만 남긴다.
3. 화면 "답변에 사용한 근거 N건"에 `[근거 N] 제목 · 출처 유형(기업정보(DART)·위키백과·DART 공시·한국은행 용어집) · 원문` 링크를 표시한다. 공시는 접수번호로 DART 원문 페이지, 용어집은 책자명과 쪽 번호.
4. 인용이 하나도 없으면 "답변에 인용된 근거가 없습니다" 안내를 표시한다.
5. 대화를 다시 그릴 때 근거 목록도 함께 저장·표시한다(이전 답변의 근거가 사라지지 않도록).

## 8. 도메인 특화 기능 설계 이유 (F2010 · F2011)

| 기능 | 왜 이 도메인에 필요한가 | 근거 사용 |
| --- | --- | --- |
| 기업 브리핑 카드 | 투자 공부를 시작하는 사람이 가장 먼저 찾는 것은 "이 회사가 뭘 하고, 누가 지배하고, 무슨 이슈가 있었나". 항목을 고정하면 빠진 정보가 "확인 불가"로 드러난다 | 4개 소제목 각 문장에 근거 번호 |
| 주장 팩트체크 | 커뮤니티·뉴스 문장을 그대로 믿는 것이 개인 투자자의 대표적 실수. "일부 사실", "출처 간 불일치"까지 판정해 어디가 틀렸는지 보여 준다 | 판정 + 근거 (예: "1969년 설립, 본사는 서울" → 일부 사실 — 설립 연도는 맞고 본사는 DART 주소상 수원) |
| 경제·금융 용어 풀이 | 공시와 기사 용어(물적분할, PER)가 진입 장벽. 한국은행 용어집으로 정확한 정의를 주고, 그 기업 문서에 직접 나올 때만 연결한다 | 용어집 쪽 번호 + 기업 문서 |
| 조건 기반 탐색 | "반도체 관련 대형주"처럼 기업명을 모를 때 시작점이 필요 | 메타 색인 텍스트에서 후보 → LLM이 근거 있는 것만 선별, 후보 밖 종목코드는 버림 |

## 9. 선택 이유와 겪은 문제 · 해결 (상세: 노션 트러블슈팅 로그)

| # | 문제 | 원인 | 해결 | 결과 |
| --- | --- | --- | --- | --- |
| 1 | Windows에서 한글 출력 깨짐 | 콘솔 cp949 + `python -I`가 PYTHON* 환경변수 무시 | 스크립트에서 UTF-8 재설정, 파일은 항상 encoding 지정 | 정상 출력 |
| 2 | P2가 질문에 나온 'LG화학' 문서까지 버림 | 규칙이 지나치게 보수적, P1 검색어가 문장형 | P1·P2 규칙 수정 + 제목=검색어 규칙 | 색인 문서 1건 → 2건 |
| 3 | 조건 탐색에서 SK하이닉스 누락 | 색인 텍스트 필드 순서, 짧은 한국어 조건의 임베딩 한계 | 개요를 앞으로 + 키워드·벡터 하이브리드 후보 | 반도체 기업 포함 |
| 4 | 브리핑이 "확인 불가"뿐, '기아' 동음이의어 문서 색인 | 긴 일반 문서가 Top-k 독차지, 정확 일치 규칙이 동음이의어도 살림 | 기업 본문서 우선 확보, 문서당 청크 상한, 동음이의어 제외, 기업명 검색어 제외 | 브리핑 4항목 근거로 채워짐, 청크 204 → 16 |
| 5 | DART 표 데이터 행 누락 | 칸 안의 `<P>`, TE·TU 칸 태그 | TR 단위 평문화 + 태그 추가 | 매출 표가 한 줄씩 색인 |
| 6 | 용어집 파싱 누락 155개, 용어 검색 부정확 | 두 줄 목차, 홀짝 쪽 머리글 차이, 짧은 한국어 용어의 임베딩 한계 | 목차 이어 붙이기·머리글 처리, 키워드 우선 검색 | 634 → 779개, 공매도·PER 정확히 매칭 |
| 7 | RAG가 근거를 엮어 '물적분할'이라고 단정 | P3 규칙에 추론 금지가 없음 | "여러 근거를 엮어 새 결론 금지" 규칙 | "문서에 직접 언급되지 않는다"로 수정 |
| 8 | 화면의 근거 수가 답변과 다름 (`[근거 7, 근거 8]` 누락, `[근거 1]~[근거 8]`을 인용으로 셈), 물결표가 취소선으로 보임 | 모델의 다양한 표기를 정규식이 가정하지 않음, Markdown 해석 | 반복 표기 파싱 · 범위 표기 제외(코드) · 물결표 이스케이프 · 회귀 테스트 | 근거 2건 → 4건(정확), 인용 없는 답은 "인용 없음" 안내 |

**공통으로 배운 점**: 한국어 짧은 키워드(기업명·용어·조건)는 임베딩보다 정확 일치가 강하고, LLM 판단이 흔들리는 곳은 규칙으로 고정하는 것이 안정적이다.

## 10. 알려진 한계와 다음 단계

- 한 질문에 두 가지를 물으면(예: "최대주주와 DS 부문 매출") 한쪽 근거가 Top-k에 들지 못할 수 있다 → 질문 분해(멀티 쿼리)
- 근거 번호가 붙어도 문장이 근거와 정확히 일치하는지는 따로 검증하지 않는다 → 문장 단위 인용 검증
- 최대주주·배당 같은 정형 수치는 검색보다 DART 정형 API 호출이 정확하다 → 도구 호출 노드
- F2013(HTML/CSS/JS 프론트엔드)은 제출 이후 진행
